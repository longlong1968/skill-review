# Skill 炼金坊修改文档

## 目标

基于现有 `skill-review` 的质量评审能力，规划一个更完整的“skill 炼金坊”工作流，用于把已经生成并经历多轮修改、但结构和功能都可能劣化的 skill 重新整理、修复、验证，并最终提升到可稳定使用的状态。

这个方案的核心不是单次 review，而是一个完整的“需求重建 -> 结构修复 -> 功能修复 -> 实测验收 -> 最终定稿”的闭环。

## 背景问题

现有 skill 在经过反复修改后，常见问题不只是格式和表达变差，还包括：

- skill 的真实目标和当前实现逐渐脱钩
- 触发条件、流程结构、约束方式和验证门禁被破坏
- 原本应满足的用户需求没有被显式记录，后续修改容易漂移
- skill 看起来更完整，但实际跑不通，或者不能稳定满足真实工作场景
- review 只能评结构质量，不能直接保证功能和目标达成

因此需要一个比 `skill-review` 更高一层的 skill，对现有 skill 做“重构 + 验收”。

## 方案定位

建议新增一个独立 skill，而不是继续把所有能力塞进 `skill-review`。

推荐定位：

- 中文展示名：`Skill 炼金坊`
- 目录名候选：`skill-foundry`、`skill-refinery`、`skill-alchemy`

推荐优先使用 `skill-foundry` 作为目录名，因为它更接近“锻造、返工、成形”的含义，也更容易让人理解这是一个面向修复和定稿的流水线 skill。

## 核心原则

### 1. 不做单次评审，做完整闭环

目标不是给出一份漂亮的 review 报告，而是把 skill 修到可验收、可复测、可继续维护。

### 2. 结构质量与功能质量分开治理

结构问题和功能问题不能混在一起改，也不能用一个模糊总分混过去。

### 3. 先冻结目标，再进入修改

进入优化前，必须先和用户确认需求、输出形式、验收标准、测试样例。没有冻结目标，就不能开始大规模重写。

### 4. 每一轮修改都必须回到验收表

任何修改都必须能回答：

- 它解决了哪条验收项
- 它影响了哪些既有能力
- 它需要补哪些回归测试

### 5. 不达到分数线，不宣布完成

除非验收评估表中所有关键项均达到门槛，否则不能宣布 skill 完成。

## 推荐工作流

### Phase 1：通读与还原

完整读取用户 skill 的全部内容：

- `SKILL.md`
- `references/`
- `scripts/`
- 必要时还包括相关 assets、历史 patch、已有 eval 样例

目标：

- 还原这个 skill 原本想解决什么问题
- 总结它当前实际上是怎么实现的
- 找出用户需求、skill 描述、skill 行为之间的偏差

产出：

- `requirements.md`
- 内容包括：
  - 用户真实目标
  - 典型输入
  - 期望输出
  - 成功标准
  - 非目标
  - 当前 skill 的实现路径摘要
  - 已知缺陷和风险点

### Phase 2：和用户确认契约

把还原出的需求和实现过程重新整理后，与用户确认：

- 需求内容是否准确
- 输出形式是否准确
- 需要达到的最终目标是什么
- 哪些边界场景必须支持
- 哪些失败是不能接受的

同时要求用户尽量提供真实工作中的任务样例，用于后续评测。

产出：

- `scorecard.md`
- `evals.json`

其中：

- `scorecard.md` 用于定义验收维度、评分方法、权重、过关阈值
- `evals.json` 用于记录测试样例、真实任务、预期行为、失败条件

### Phase 3：第一轮优化，先修结构

这一轮只做结构修复，原则上不改变 skill 的业务目标。

使用 `skill-review` 的方法，重点检查并修复：

- description 是否仍然是触发条件驱动
- 认知结构是否清晰
- 是否存在负向约束缺失
- 是否有验证门禁
- 是否存在 references/scripts 放置不合理
- Integration 是否清楚

目标：

- 让 skill 在结构上重新变得清晰、可触发、可维护
- 避免一边修功能，一边继续在糟糕结构上堆东西

### Phase 4：第二轮优化，再修功能

这一轮不再只看结构，而是对照前面冻结的需求契约，检查当前 skill 是否真的能：

- 满足用户需求
- 达到指定目标
- 产出正确形式的结果
- 覆盖关键输入场景
- 在边界条件下保持可接受行为

如果不能，则修改：

- `SKILL.md` 中的流程和规则
- `references/` 中的参考材料
- `scripts/` 中的执行逻辑
- 必要的验证步骤和输出约束

注意：这一步不是“润色”，而是“对功能进行重构和补足”。

### Phase 5：实测验收循环

对照 `evals.json` 和 `scorecard.md` 做实际测试。

测试后需要：

- 给每条验收项打分
- 标出低于阈值的项目
- 分析失败原因
- 形成定点修复方案
- 修改后重新测试

要求：

- 验收评估表中的所有关键项都必须达到 90 分以上
- 任何致命失败项都不能被平均分掩盖

建议采用两层门禁：

- 核心功能项：每项 >= 90
- 总体加权平均：>= 90

### Phase 6：最终结构复检

当功能和验收结果都达标后，再使用 `skill-review` 的标准做最后一次结构检查。

目的：

- 防止为了修功能而把 skill 重新改成结构混乱的状态
- 确保最终版本既“能用”，又“像一个高质量 skill”

## 推荐工件

为了避免流程漂移，建议整个炼金流程固定产出以下工件：

### 1. `requirements.md`

记录：

- 真实需求
- 输入输出定义
- 使用场景
- 非目标
- 当前 skill 的实现摘要

### 2. `scorecard.md`

记录：

- 验收维度
- 每项权重
- 打分标准
- 过关线
- 致命失败项定义

### 3. `evals.json`

记录：

- 测试样例
- 样例来源
- 预期输出
- 失败条件
- 是否来自真实工作场景

### 4. `remediation-plan.md`

记录每一轮：

- 问题定位
- 修改目标
- 影响范围
- 回归测试项
- 当前风险

## 评分设计建议

不要只使用一个笼统总分，建议分成两类分数：

### A. 结构分

建议维度：

- 触发准确性
- 认知结构清晰度
- 负向约束完整性
- 验证门禁完整性
- 可维护性

### B. 功能分

建议维度：

- 核心任务完成度
- 输出形式符合度
- 对真实样例的稳定性
- 异常和边界处理能力
- 与用户目标的一致性

### 通过规则

- 所有核心功能项不得低于 90
- 总体加权平均不得低于 90
- 存在致命失败项时直接不通过

## 对 skill-review 的关系建议

`skill-review` 不应直接扩展成整个炼金坊，而应保持其“结构评审器”的定位。

推荐关系：

- `skill-review`：负责结构质量、表达质量、流程组织质量
- `skill-foundry`：负责需求重建、契约确认、功能修复、实测验收、最终定稿

也就是说，`skill-review` 是 `skill-foundry` 的一个子能力，而不是反过来。

## 需要新增的关键机制

### 1. 需求冻结

在进入修改前，明确本轮要达成的目标和不变项，避免修改过程中目标漂移。

### 2. 变更影响分析

每次修改后都要回答：

- 这次改动修复了什么
- 可能影响哪些旧能力
- 需要补跑哪些测试

### 3. 终局门禁

未通过验收表时，禁止宣布完成。

### 4. 用户样例注入

允许用户在 Phase 2 提供真实工作任务，用作高优先级测试样例。

### 5. 最终回归 review

在功能修复完成后，再做一次结构 review，防止修功能时引入新的结构退化。

## 为什么不建议把所有能力继续堆到 skill-review 里

如果把需求还原、契约确认、结构重构、功能重构、测试验收、回归 review 全部继续塞进 `skill-review`，会产生几个问题：

- skill 本体过长，认知负担过大
- 结构评审和功能验收相互污染
- 输出不再聚焦，容易变成“一份什么都想做的 prompt”
- 后续维护会更困难

因此更合理的方式是：

- 保持 `skill-review` 小而硬，专注结构质量
- 新建 `skill-foundry` 作为总控 skill
- 在 `skill-foundry` 中调用 `skill-review` 的评审思路

## 第一版实现建议

第一版不必追求全自动，可以先做成“结构清晰、工件固定、流程可执行”的版本。

建议第一版至少包含：

- 明确的 6 阶段流程
- 固定的 4 份工件模板
- scorecard 打分规则
- eval 样例格式
- 最终门禁规则

可以暂缓的能力：

- 自动化 benchmark 汇总
- 多版本 diff review
- 自动生成 patch 建议
- 全自动脚本化回归

这些适合在第一版跑通后再加。

## 后续落地建议

下一步可以继续产出以下内容：

1. `skill-foundry/SKILL.md` 的第一版骨架
2. `references/scorecard-template.md`
3. `references/requirements-template.md`
4. `references/remediation-template.md`
5. `evals/evals.schema.json` 或示例 `evals.json`

## 当前结论

这个“炼金坊”想法是合理的，而且比单纯加强 `skill-review` 更有价值。

它的关键不是“再多写一点 review 规则”，而是把 skill 优化这件事从“凭感觉润色”升级为“先还原需求，再冻结契约，再分阶段修复，再按验收表反复实测，最后定稿”的工程化流程。

如果后续正式实现，建议将它作为独立 skill `skill-foundry` 落地，并把 `skill-review` 作为其中的结构评审模块保留。
